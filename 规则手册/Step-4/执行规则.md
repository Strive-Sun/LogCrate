# LogCrate 执行规则

本文件只规定任务如何开始、排序、实施、恢复和结束。工作状态的读写与闭环以 `规则手册/Step-2/工作约束.md` 为准；所有自测、测试、边界、门禁、失败处置及证据要求统一以 `规则手册/Step-5/验证规则.md` 为准。

开始或继续任何需求前，必须依次完成 `规则手册/Step-0/OPENSPEC.md`、`规则手册/Step-1/项目配置.md`、`规则手册/Step-2/工作约束.md` 和 `规则手册/Step-3/工作状态.md`，再完整读取本文件，随后读取验证规则。

## 权威与开始

- 需求、设计、任务状态、验证证据和工作检查点分别以仓库指定的权威文档为准，不以聊天摘要或模型记忆为准。
- 实现前确认任务范围、工作区现有改动、验收条件和验证入口；不得覆盖来源不明的用户改动。
- 不猜测构建、测试、发布或迁移命令；命令必须来自仓库文件、工具帮助或已验证说明。
- 新能力、公共行为变化、破坏性变更、架构调整以及重大性能或安全工作，必须先完成 OpenSpec 要求的提案、校验和审批。
- 规则或文档与仓库事实冲突时先进行只读核对；无法消解时停止有影响的操作并请求维护者裁决。

## 任务顺序

- 执行单位是任务文档中最小编号的叶子任务，例如 `1.1`；没有任务文档的普通需求整体视为一个执行单位，除非先明确拆出小节清单。
- 严格按编号和依赖顺序执行，一次只允许一个最小任务处于进行中，不得预先实现后续任务。
- `1.1` 的实现、验证、交接、所需状态更新和独立 commit 未全部完成前，不得开始或标记 `1.2`；具体门禁以 `Step-5/验证规则.md` 为准。
- 任务没有编号、依赖或验收条件不明确时，先修订任务文档，不自行假定顺序。

## 自动提交

- 每个最小任务通过 Step-5 门禁后自动创建一个本地 commit；提交成功是进入下一任务的必要条件。
- 提交前更新对应任务勾选，并按 Step-2 判断是否更新工作状态交接；随后复核该小节的最终差异与验证结论。
- 只显式暂存该小节的实现、测试、规格、任务状态和交接文件；禁止使用 `git add .`、`git add -A` 或通配方式带入用户已有、来源不明或后续任务改动。
- commit 信息使用项目约定前缀并包含任务编号与结果，例如 `feat: 1.1 完成书签配置迁移`。
- 提交后核对 commit 内容和剩余 `git status`；当前小节仍有应提交的改动、提交失败或误含无关文件时，不得进入下一任务。
- 自动提交仅限本地 commit，不自动 push、创建 tag、归档 OpenSpec change、发布或修改远端状态。
- 不修改、压缩或 amend 已有提交，除非用户明确要求。

## OpenSpec 与方案变化

- 是否创建 change 按 `Step-0/OPENSPEC.md` 和 `openspec/AGENTS.md` 判断；需要 proposal 时，批准前不得实施产品变更。
- 若当前任务改变需求、架构、验收语义或后续方案，先更新对应 proposal、design、delta spec、tasks 和验证标准。
- OpenSpec 文档更新后按 `Step-0/OPENSPEC.md` 完成相应流程；缺少所需批准时不得继续产品实现。
- 新发现不自动扩大当前范围：影响当前正确性或验收的事项当前处理；改变方案的事项先更新权威文档；独立事项进入明确的后续去向。

## 工作状态与恢复

- 是否建立、更新或只读核对工作状态，统一按 Step-2 判断；不得把 Step-3 当作每轮机械改写的完成账本。
- 需要持久化现场时，继续使用 Step-3 的现有结构记录任务、现场、证据、发现、下一步和详细交接，不另建重复台账。
- 暂停或恢复时核对任务文档、工作约束、工作状态、验证证据、`git status`、相关差异和关键文件；无法核对的内容标记为待确认并继续只读调查。
- 提交后的实际哈希通过 Git 和最终交付说明报告；禁止为回写哈希或关闭旧现场创建额外提交或 amend。

## 完成条件

- 任务是否完成以 `Step-2/工作约束.md` 的闭环条件和 `Step-5/验证规则.md` 的门禁与证据结论为准；未达到完成条件时不得进入后续任务。
- 任务状态必须实时反映实际实施与 Step-5 验证结论，不得根据预期批量补勾。
