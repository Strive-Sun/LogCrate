# LogCrate 工作约束

本文件规定任务现场何时需要写入 `规则手册/Step-3/工作状态.md`，以及状态如何随验证和本地提交闭环。它只定义工作状态的使用约束，不保存具体任务现场，也不替代任务清单、验证证据或 Git 历史。

## 1. 职责边界

- `Step-2/工作约束.md`：规定工作状态的读取、写入、恢复和闭环条件。
- `Step-3/工作状态.md`：保存截至最近更新时间的任务现场、发现、验证证据与交接；保留既有结构和历史记录。
- `Step-4/执行规则.md`：规定最小任务的串行实施和独立提交。
- `Step-5/验证规则.md`：唯一决定验证等级、完成门禁和证据要求。
- 任务清单反映实施状态，Git 历史反映实际提交；工作状态是恢复辅助记录，不单独证明任务已经完成。

## 2. 每次任务的进入检查

1. 完整读取工作状态，并用当前任务文档、`git status`、相关差异和最近 Git 历史核对其更新时间与现场。
2. 若状态记录为“已完成（以本次本地提交成功为生效条件）”或等价的待提交阶段，且 Git 已存在范围、任务标识和提交信息一致的提交，则该记录视为已闭环的历史现场，不阻止新任务。
3. 若状态显示进行中、阻塞、待验证或待提交，而 Git 事实不能证明已经闭环，则先恢复该任务，不得直接开始后续任务。
4. 状态、任务文档和 Git 无法相互印证时，先只读调查并标记待确认；不得用聊天记忆覆盖仓库事实。
5. 始终区分当前任务改动、用户已有改动、来源不明改动和生成物，禁止把无关现场混入提交。

## 3. 何时改写工作状态

以下任一条件成立时，必须建立或更新工作状态：

- 任务跨会话、长时间运行、高风险，或包含多个最小编号任务。
- 当前工作需要暂停、等待人工/真机验证、外部条件或维护者决策。
- 出现失败、警告、未验证项、文档冲突、来源不明改动、方案变化或需要后续处理的发现。
- 如果不记录准确停止位置、证据和下一步，下一位执行者无法仅凭仓库恢复。

普通问答、只读调查，以及能够在当前会话内完成、验证并提交且没有未决事项的单一短任务，只需读取和核对工作状态，不为记录过程而改写它。任务一旦命中上述条件，立即升级为需要持久化状态的任务。

## 4. 状态更新时机

- 开始需要持久化的任务时，记录当前最小任务、基准提交、允许范围和下一步。
- 每个最小任务仍严格串行；出现重要发现、阻塞、暂停或验证结论变化时，在继续或交接前更新对应现场。
- 提交前完成 Step-5 门禁、详细交接和适用的任务勾选，再把状态写为“待提交”或“已完成（以本次本地提交成功为生效条件）”等准确表述，并将该状态更新包含在同一个目标 commit 中。
- 提交成功后，以 Git 历史、提交范围、任务状态和 Step-5 证据共同判定闭环；实际 commit 哈希在最终交付说明中报告，不回写工作状态。
- 不得仅为记录 commit 哈希或关闭旧现场创建第二个 bookkeeping commit，也不得为此 amend 已有提交。

## 5. 完成与后续任务

只有同时满足以下条件，当前最小任务才完成：

1. 实现范围完整且未混入后续任务。
2. Step-5 要求的验证与交接通过，没有当前范围内的失败、阻断或未分类发现。
3. 适用的任务项已勾选，状态更新要求已经满足。
4. 独立本地 commit 创建成功、范围正确，当前任务没有应提交而遗留在工作区的改动。

任一条件不成立时不得开始或标记下一任务。普通短任务没有任务清单或持久化状态要求时，对应条件视为不适用，但验证和独立提交仍不可省略。

## 6. 交付与恢复

- 最终交付说明报告任务范围、验证等级、实际命令或人工步骤、准确结果和实际 commit 哈希。
- 需要持久化状态的任务暂停或结束时，逐项列出所有未处理问题；确实没有时明确写“未发现未处理问题”。
- 恢复任务时只补做尚未完成或证据已失效的步骤，不因状态文档仍保留历史现场而重复已由 Git 和有效证据证明完成的工作。
