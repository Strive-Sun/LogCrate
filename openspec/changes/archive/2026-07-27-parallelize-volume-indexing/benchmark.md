# Windows 多卷索引基准

## 目标耗时

以下目标适用于当前基准设备、Release 构建以及 C:\ 约 308 万条、D:\ 约 280 万条 MFT 记录的规模，使用至少 3 次可比样本的中位数验收：

| 里程碑 | 预期上限 |
| --- | ---: |
| 所有卷离开 `pending` | 2 秒 |
| 单卷 MFT 枚举 | 20 秒 |
| 首批结果可搜索 | 30 秒 |
| C:\ 与 D:\ 全部结果可搜索 | 60 秒 |
| 最后一个卷可搜索至全局 `ready` | 2 秒 |
| SQLite/USN 后台持久化完成 | 5 分钟 |
| 重建期间 UI 输入响应 p95 | 100 毫秒 |

查询索引达到“全部结果可搜索”后即视为用户可见的索引完成。后台持久化可以继续，但不得阻塞查询，也不得让界面继续显示“正在建立索引”。当记录规模超出当前基准的 ±10% 时，同时使用吞吐率验收：MFT 枚举中位吞吐不低于每秒 15 万条记录，路径解析与查询索引合并中位吞吐不低于每秒 8 万个可搜索文件。

完整路径 token 增加了查询索引写入量：相对调整前单卷查询可用基准，C:\ 从 28,084 ms 增至 31,543 ms，回退约 12.3%；D:\ 从 23,770 ms 增至 27,985 ms，回退约 17.7%。该回退换取了 SQLite 持久化期间可直接搜索完整路径。真实应用会并行枚举但由单 writer 合并两卷，必须另行执行三次完整应用级重建，不能用两个单卷样本相加或取最大值代替“全部卷 ≤60 秒”和“首次结果 ≤30 秒”的验收结果。

快速阶段测试还确认，首批路径回调不等于用户可查询：原实现直到完整 staging 索引原子切换后才查询新快照。当前方案已调整为全局 `scanning` 时读取已提交的 staging 部分结果，正常状态和中断恢复仍读取旧 active 快照；新增单元测试覆盖两种查询来源。真实应用的首次可搜索耗时仍需任务 4.6 的三轮完整运行验证。

应用级旧实现对 D 盘执行相同查询索引阶段超过 12 分钟仍未完成。原因不是 MFT 卡住，而是协调线程逐文件惰性解析目录、拼接路径，并在批量模式下反复提交 Tantivy 小段。优化后先缓存目录树，再以最多 4 个后台生产线程并行生成文件路径和查询文档；共享 Tantivy writer 仍由单一协调流程管理。

启动恢复实测中，D 盘首批可搜索结果在 `12,329 ms` 出现，完整增量查询索引在 `66,395 ms` 完成。增量模式需要删除旧路径 term 后再新增，因此慢于干净暂存索引，但不会再等待其它卷的昂贵 USN 合并。

## SQLite 持久化

D 盘完整测试分别记录查询可用、文件表完成和 NTFS 节点表完成时间：

| 实现 | 查询可用 | 文件表完成 | 节点表完成 |
| --- | ---: | ---: | ---: |
| 优化前 | 23,288 ms | 195,369 ms | 254,668 ms |
| 优化后 | 23,448 ms | 133,042 ms | 179,750 ms |

单卷最终持久化缩短 `29.4%`，文件表阶段缩短 `31.9%`。优化后每卷使用一个原子事务，并将多值 SQL 批次提高到 SQLite 参数上限内的 3,000/5,000 行。查询索引约 23 秒即可使用，后续 SQLite/USN 快照保存仍在后台执行。
