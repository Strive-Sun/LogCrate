## Context

LogCrate Index Service 已允许最多 4 个并发本机 IPC 客户端，并为每个连接使用独立工作线程。瓶颈位于 GUI 后端的搜索协调器：首次重建与启动恢复仍逐卷调用服务，并在同一循环中完成路径解析、查询索引写入和持久化，因此后续卷长期停留在 `pending`。

SQLite 只有一个写入者，Tantivy 也由一个 `IndexWriter` 管理。简单地为每个卷启动完整独立进程并让它们共同写同一索引，会重新引入 `database is locked`、Tantivy writer lock 和提交顺序不确定问题。

## Goals / Non-Goals

- Goals:
  - 本地固定 NTFS 卷并行枚举或追赶，不因前一个卷耗时而保持 `pending`。
  - 先完成卷的搜索结果尽快可查询。
  - 每卷错误隔离，最终状态和全局完成条件准确。
  - 状态文字和计数反映每卷实际执行阶段，不使用无法解释的全局 `0 MFT` 提示。
  - 所有卷查询结果可用后，全局状态不依赖文件系统事件流静默，并在有界时间内收敛到 `ready`。
  - 目录级 USN 恢复成本可预测，不因全图遍历退化到几十分钟或数小时。
  - 总耗时、阶段耗时和全局计数具有明确且可验证的语义。
  - 使用同一设备、同一 C:\/D:\ 范围记录可复现的串行与并行耗时对比。
  - 保持 UI 线程无磁盘扫描、路径重建和索引写入工作。
- Non-Goals:
  - 为每个卷安装或启动一个独立 Windows 服务实例。
  - 允许多个进程直接写同一个 SQLite 或 Tantivy 索引目录。
  - 增加新的数据库表、Tantivy 字段或扩大索引服务权限。
  - 保证文件系统在索引完成瞬间不再产生任何新事件。

## Decisions

- Decision: 使用有界的卷级后台 worker，并行度不超过索引服务并发上限和待处理卷数。每个 worker 建立独立 IPC 连接，执行一个卷的 MFT 枚举或 USN 读取。
- Decision: 卷 worker 只产生有界批次或卷任务结果；共享 Tantivy/SQLite 的变更由单一协调器合并。数据库写入仍受现有 operation 生命周期保护，不允许旧 generation 写入。
- Decision: 首次全量重建按“发现/路径解析/查询索引合并/持久化”阶段发布状态。所有卷在被调度后立即从 `pending` 进入 `scanning`；等待共享 writer 时显示 `merging`，避免把实际工作误报为挂起。
- Decision: 每卷状态分别保存操作开始时间、当前阶段开始时间、完成时间、操作总耗时和当前阶段耗时。进入新阶段时重置阶段计时；进入 `ready`、`fallback` 或 `error` 时冻结完成耗时。阶段至少区分 `connecting`、`readingUsn`、`enumeratingMft`、`resolvingPaths`、`merging`、`persisting`、`handoff`、`ready` 与 `fallback`。
- Decision: 在收到首个 MFT 批次前，UI 显示“正在连接索引服务”或“正在读取 MFT”，不显示“已发现 0 条 MFT 记录”；收到批次后才显示实际计数。进入路径解析或合并后保留最终发现数并独立更新可搜索数。
- Decision: 协调器按完成顺序消费卷结果，使小卷或快速卷无需等待最慢卷。所有卷的查询索引快照达到终态后立即发布全局 `ready`，不得等待 SQLite/USN 持久化或事件队列静默。watcher 从操作开始持续把事件写入有界队列；持久化结束后协调器执行一次最多 4 批、最多 500 毫秒的事件交接，再把同一接收队列移交常驻增量 worker。队列溢出通过既有 dirty 标记触发范围重建，不把溢出误报为已完整处理。
- Decision: `scanned_files` 始终等于所有卷 `discovered_records` 之和，`indexed_files` 始终等于所有卷 `searchable_files` 之和。数据库总数只用于一致性核验和诊断，不作为批量恢复期间覆盖多卷汇总状态的替代来源。
- Decision: USN 恢复在执行前分类变化。普通文件变化继续走按文件快速路径；只要目录变化会要求加载或遍历整个卷节点图，当前版本就直接将该卷降级为全量 MFT 重建。后续只有在能够按受影响子树有界解析后，才恢复目录级增量路径。降级原因和所选策略写入诊断日志，但不作为错误展示。
- Decision: 若目录变化发生在 MFT 枚举完成到 SQLite/USN 持久化结束的窗口内，系统不得再次进入全图增量算法。当前查询快照保持可用，卷快照以 `snapshot_complete=false` 保存，当前会话由已安装的文件 watcher 事件补齐，下次启动对该卷执行全量 MFT 重建。该策略及原因必须写入日志，不能把不完整快照标记为成功。
- Decision: 为每卷记录 `enumeratingMft`、`resolvingPaths`、`merging`、`persisting` 和 `handoff` 的开始、结束、记录数与策略。超过基准门槛的阶段必须能从日志中单独识别，不再只输出无法定位瓶颈的生命周期总耗时。
- Decision: 性能验收使用当前基准设备、Release 构建、C:\ 约 308 万条和 D:\ 约 280 万条 MFT 记录。三次可比样本的中位数目标为：所有卷离开 `pending` 不超过 2 秒；单卷 MFT 枚举不超过 20 秒；首批可搜索结果不超过 30 秒；C:\ 与 D:\ 全部结果可搜索不超过 60 秒；最后一个卷可搜索后全局状态不超过 2 秒进入 `ready`；SQLite/USN 后台持久化不超过 5 分钟。持久化可继续在后台执行，但 MUST NOT 阻塞查询或让全局状态继续显示正在建立索引。
- Decision: 对文件数量明显不同的设备同时记录吞吐率。全量 MFT 枚举中位吞吐不得低于每秒 15 万条记录，路径解析与查询索引合并的中位吞吐不得低于每秒 8 万个可搜索文件；绝对耗时目标仅对记录数处于基准规模 ±10% 的样本强制适用。
- Decision: 查询索引进入 `ready` 后，包含 Windows 或 Unix 路径分隔符的搜索也使用 Tantivy/Orange 查询索引；分词器已将 `: / \\` 等分隔符安全拆成路径 token。SQLite 只在查询索引不可用时回退，避免路径搜索被后台持久化进度阻塞。
- Decision: 全量重建使用 staging 索引时，正常状态仍查询旧 active 快照以保证中断恢复；当全局状态为 `scanning` 且 staging 已至少完成一次按卷提交后，搜索请求改为读取 staging 并标记为 partial，使先完成卷的结果无需等待其它卷。最终仍通过原子目录切换发布完整快照。
- Decision: 单卷快速 provider 失败时只让该卷进入兼容扫描或错误状态，其它卷继续；取消或重建通过 generation 让全部 worker 尽快停止，协调器等待 worker 退出后再清理共享索引。
- Decision: 不采用“每卷一个独立进程直接产出最终共享索引”。现有服务进程已经隔离提权扫描并提供并发；增加服务副本只会扩大安装、IPC、取消和数据库锁复杂度，不改善单 writer 合并瓶颈。
- Decision: 修改代码前使用当前串行实现建立基准，修改后在相同构建模式、相同 C:\/D:\ 搜索范围和未发生显著文件变化的条件下各执行至少 3 次全量重建。记录点击重建到所有卷离开 `pending`、首批可搜索结果、每卷 MFT 枚举完成、每卷查询索引可用、全部卷可搜索和持久化完成的单调时钟耗时，并形成 `benchmark.md`。
- Decision: 验收以中位数比较。并行版本的“全部卷可搜索”中位耗时必须低于串行基线，首批可搜索结果不得比基线回退超过 10%，重建期间 UI 输入响应 p95 仍不超过既有 100 毫秒门槛。

## Risks / Trade-offs

- 同时保存多个大卷 MFT 快照会增加峰值内存 → worker 使用有界通道发送批次，协调器限制在途数据；不得为所有卷长期保留第二份完整路径列表。
- 多磁盘并发会增加 CPU 与 I/O 压力 → 并行度有界，索引写入保持单协调器，并保留 UI 响应性能门槛。
- 两次基准之间文件系统可能变化 → 记录每卷发现记录数和可搜索文件数，明显变化的样本不参与直接耗时比较并重新测量。
- 某个 IPC 连接阻塞可能延迟全局完成 → 独立卷状态与错误隔离确保其它卷仍可合并和查询。
- 取消期间 worker 仍可能处于系统调用 → 关闭对应 pipe 作为枚举取消信号，并在清理共享索引前等待 worker 退出。
- 查询进入 `ready` 时持久化窗口内的事件尚未提交 → watcher 已从索引操作开始持续收集事件；持久化结束后有界消费并移交同一队列，队列溢出则保留 dirty 标记并触发范围重建。`ready` 表示基线查询快照完整可用，而不是所有后续文件变化都已静默。
- 目录变化直接全量重建会增加少量变更时的固定成本 → 当前实测全量路径可在可预测的分钟级完成，优先避免全图增量算法退化；未来以受影响子树算法替换该保护策略。
- 后台持久化完成晚于查询可用 → 状态明确区分“查询索引已就绪”和诊断中的“持久化完成”；崩溃恢复继续依赖原子事务和恢复标记，不向用户展示虚假的索引未完成状态。

## Migration Plan

不迁移数据库结构。新协调器读取现有每卷快照并分别执行 USN 追赶；快照无效的卷单独重建。出现异常时可回退到现有串行调度实现，而不删除用户索引。

## Open Questions

### 已知问题：Windows 重建完成阶段偶发 `os error 5`

- 2026-07-26 真机重建索引时，界面提示“搜索索引失败：拒绝访问。（os error 5）”。本轮仅完成只读诊断，尚未实施修复。
- 已确认实际搜索数据目录为 `%APPDATA%\com.logcrate.app\file-search`，当前用户对该目录具有完全控制权限，因此没有证据表明问题来自 AppData 根目录 ACL 配置错误。
- 故障期间曾观察到活动查询索引 `file-search-orange-gpl-v1` 与 staging 索引 `file-search-orange-gpl-v1.next` 同时存在；随后 `.next` 消失且活动索引更新时间推进，说明错误发生在全量构建后期或 staging/active 切换附近，而不是 MFT 枚举开始之前。
- 当前首要怀疑点是 `activate_staged_query_index()` 在 Windows 上执行活动目录重命名、staging 目录切换或旧 `.previous` 目录删除时，Tantivy mmap/reader/writer、另一个 LogCrate 进程或杀毒软件仍短暂持有文件句柄。现有错误链只保留原始 `std::io::Error`，没有操作名称和目标路径，因此该原因尚未被完全证实。
- 后续处理 MUST 先为 staging 清理、active/previous 重命名及旧快照删除补充“阶段 + 源路径 + 目标路径”的错误上下文和诊断日志，再根据确定的失败操作处理句柄释放或 Windows 有界重试；不得通过静默忽略错误伪装成功。
- 修复验收 MUST 覆盖 Windows 上已有活动索引时的连续重建、查询并发读取期间切换、遗留 `.next`/`.previous` 恢复，以及失败后旧活动索引仍可查询。若外部进程持续占用超过重试窗口，界面必须显示可定位的阶段和路径，不能只显示 `os error 5`。

- 当前 Tantivy schema 没有可按卷直接删除的字段，因此启动恢复中的单卷全量重建必须等 SQLite 持久化和旧路径变更提交后，才能保证该卷查询结果完全去除旧路径；首次全量重建使用空的 staging 查询索引，不受此限制。后续若要让“单卷恢复”也在 60 秒内完整可搜索，需要增加可按卷删除的索引字段或建立按卷独立 segment，此项不在本轮 schema 兼容范围内。
