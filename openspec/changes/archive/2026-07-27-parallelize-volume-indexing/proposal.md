# Change: 并行建立多卷搜索索引

## Why

当前 Windows 搜索协调器按卷串行执行 MFT 枚举、USN 追赶和索引恢复。当前一个卷扫描时，其余卷会长期显示 `pending`，拥有多个大容量磁盘的用户必须等待前一个卷完成后才能看到后续卷结果。

现有全局提示还会在卷状态为 `scanning` 时长期显示“已发现 0 条 MFT 记录”，因为它没有区分连接索引服务、读取 USN、枚举 MFT、重建路径和合并查询索引等阶段，也没有保存每卷计数。这使用户无法判断索引是否真的在推进。

并行实现完成后，实机还暴露出两个收敛问题：即使所有卷已经达到 `ready`，全局状态仍可能因为持续排空文件监控事件而永久停留在 `scanning`；目录级 USN 变化还可能触发数百万节点的全图加载、复制和多轮遍历，使原本应在几十秒到数分钟内完成的恢复延长到几十分钟甚至数小时。现有累计耗时和全局可搜索计数也无法准确说明时间花在哪个阶段、结果是否已覆盖所有卷。

## What Changes

- 将 Windows NTFS 卷的全量枚举、恢复和 USN 追赶改为有界卷级并行任务，使所有待处理卷立即进入实际工作状态。
- 复用 LogCrate Index Service 已有的并发 IPC 能力；不启动多个可同时写数据库的服务副本。
- 由普通用户进程中的单一协调器汇总各卷任务，串行提交共享 Tantivy/SQLite 状态，避免数据库写锁竞争。
- 为每个卷独立发布 `pending`、`scanning`、`merging`、`ready` 或 `fallback` 状态；单卷失败不得阻塞其它卷完成。
- 为每个卷发布真实的当前阶段、已发现 MFT 记录数、已可搜索文件数和阶段耗时；尚未收到首批记录时不得误报“已发现 0 条 MFT 记录”为扫描成果。
- 在已有部分索引可查询的前提下持续合并先完成卷的结果，不等待最慢卷才提供新结果。
- 将有限的索引构建任务与无限的文件事件流解耦；所有卷查询快照完成后，全局状态必须在有界交接时间内进入 `ready`，后续事件由常驻增量 worker 处理。
- 分离每卷操作总耗时、当前阶段耗时和完成耗时，并记录 MFT 枚举、路径解析、查询索引合并、持久化与事件交接的独立耗时。
- 全局发现数和可搜索数始终由每卷快照汇总，不使用旧查询快照或单卷数据库计数冒充多卷总数。
- 为目录级 USN 变化增加成本保护；当增量恢复需要全图处理或预计成本超过全量重建时，自动切换为对应卷的全量 MFT 重建。
- 在当前基准设备、Release 构建以及 C:\ 与 D:\ 合计约 590 万条 MFT 记录的测试规模下，将首次结果、全部卷可搜索、状态收敛和后台持久化分别设定明确耗时目标；查询可用后不再因持久化或持续文件事件继续显示“正在建立索引”。
- 在修改前记录 C:\ 与 D:\ 串行全量重建基准，修改后使用相同范围和数据重复测量，对比各卷扫描时间、首批结果时间、全部卷可搜索时间和状态计数准确性。

## Impact

- Affected specs: `file-search`
- Affected code: `src-tauri/src/search.rs`、Windows NTFS 索引服务 IPC 调度、文件事件交接、前端搜索状态展示与对应测试
- Data compatibility: SQLite 结构和每卷 USN 快照格式保持不变；查询 token 从“仅文件名”扩展为“规范化完整路径”，内部 schema 版本由 8 提升到 9，并自动重建当前开发期本地索引，不保留旧开发索引兼容负担
