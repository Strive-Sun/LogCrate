# Change: 完善多卷索引的数量无关可扩展性

## Why

当前多卷索引把卷 worker 上限与 Windows named pipe 实例上限都设为 4；当活跃连接达到上限时，服务端会继续创建下一监听实例并可能退出。与此同时，已完成卷的完整 MFT 记录会累计等待统一持久化，使峰值内存随卷总数和全部记录数增长。四卷设备已经暴露该边界，更多固定卷、VHD 或未来挂载点会放大服务可用性、内存和失败隔离问题。

## What Changes

- 将“卷数量”和“并发资源上限”解耦：任意已发现范围登记在只保存身份/状态的轻量 scope 注册表中，固定大小 runnable window 分批装载可运行任务，并发度由统一资源预算决定。只允许不可避免的 O(N) 轻量身份/状态元数据增长，活跃重资源不随卷数量增长。
- 将索引服务的连接接纳与业务 worker 容量解耦；容量已满时返回稳定的可重试结果，服务保持运行并保留监听能力。
- 增加客户端对 pipe 忙、服务停止和启动中状态的分类恢复，避免固定等待后统一报告 `notReady`。
- 使用有界、可取消的批次流水线和按卷暂存，禁止在内存中累计所有卷的完整 MFT 快照；每卷完成后及时持久化并释放资源。
- 明确单卷失败、服务短暂重启和慢卷不得终止其它卷或使已完成范围失去查询能力；失败卷必须进入持久化自动恢复队列，不能成为可接受完成状态。
- 增加“所有范围完成”门禁：只有当前 operation scope 中每个卷的查询索引都发布并通过完整性核对，全局查询状态才能进入 `ready`；后台持久化与事件交接另以 `converged` 表示完整收敛。
- 将物理损坏、卷已拔除和权限拒绝定义为可诊断的逐卷 `blocked` 终态：停止索引动画和主动重试，显示准确原因及处理动作；其它卷完成后全局进入“需要处理”而不是一直显示“正在索引”。
- `blocked` 仅允许明确介质/设备损坏、原卷不存在或离线、访问被拒绝三类证据；协议不兼容、服务损坏、启动失败等软件故障必须自动修复或降级到可完成索引的兼容 provider，不得进入永久 `blocked`。
- 恢复状态绑定稳定卷身份而非盘符；断开卷以卷到达事件唤醒，辅以不执行 MFT 扫描、不显示索引动画的低频轻量健康探测。
- 除上述三类外部不可满足条件外，pipe 饱和、服务崩溃、协议/安装异常、暂时忙、暂时 IO、暂存损坏以及应用被用户关闭、操作系统终止后再次正常启动等中断 MUST 自动恢复，且对应卷最终必须达到 `ready` 并在后台达到 `converged`。
- 搜索索引、provider、服务或恢复故障 MUST NOT 主动关闭、重启或要求用户重启 LogCrate；当前进程仍存活时只允许后台恢复，持久化恢复状态仅用于应用下一次自然启动后继续。
- 增加 1、4、5、10 和大规模模拟范围的容量、内存、故障恢复与真实 Windows IPC 验收，注入故障解除后所有范围必须最终完成。

## Impact

- Affected specs: `file-search`(MODIFIED:多卷并行索引调度、可验证的卷索引进度、有界索引完成与持续增量维护、多卷并行性能对比;ADDED:有界接纳与恢复、快照流水线、规模矩阵、查询完成与持久化收敛门禁、阻塞终态、稳定卷身份、最终成功保证)
- Affected code: `src-tauri/src/ntfs/ipc.rs`、`src-tauri/src/bin/logcrate_index_service.rs`、`src-tauri/src/search.rs`、搜索状态与设置界面、Windows 索引服务测试和性能基线
- 数据与权限：不扩大索引内容、服务权限或网络能力；现有 SQLite/Tantivy 数据应保持兼容
- 行为变化：多卷错误从全局终止调整为按卷自动恢复；外部不可满足条件进入明确的“需要处理”终态而非无限索引，除此之外的故障必须恢复成功；任何未成功卷仍阻止全局 `ready`
