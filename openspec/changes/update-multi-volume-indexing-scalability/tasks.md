- [x] 1.1 分离 named pipe 接纳容量与业务 worker 容量，固定首版 `W = 4`；accept loop 在业务槽位占满时复用 v2 `Response::Error { code: 429 }` 返回可重试忙响应并继续监听，不退出服务。
- [x] 1.2 增加真实 pipe 饱和、额外客户端、分阶段重连、客户端断开和服务停止的服务端回归,证明容量已满不终止服务、正常断开不泄漏 pipe 或业务槽位。
- [x] 1.3 实现客户端 pipe/SCM 状态分类（容量忙、pipe 不存在、服务启动中、服务已停止、访问拒绝、协议不兼容）与分轮有界退避；协议/安装/启动软件故障不得直接归为 `blocked`。
- [x] 1.4 实现客户端单轮最多一次自动启动/重连，并在快速服务软件故障且卷可读时自动降级到兼容 provider；UAC 修复仅由用户显式触发，不在本任务用盘符代替稳定卷身份建立跨轮恢复。

## 3. 多卷协调与完成门禁

- [x] 3.1 将协调器改为 O(N) 轻量 scope 注册表、固定 `Q = 2W` runnable window 与 `W = 4` worker 池，实现分页补充、有界任务领取、完成即消费和按卷释放，保持共享 SQLite/Tantivy 单一协调写入。
- [x] 3.2 实现稳定 `volume_id`（规范化 Volume GUID path，卷序列号与文件系统类型校验）与盘符/挂载路径分离，将 scope、generation、暂存和 USN 恢复绑定到稳定身份，隔离盘符复用的不同卷。
- [x] 3.3 冻结带 generation 的 operation scope，逐卷跟踪发现、查询索引发布与查询计数核对，实现“所有范围查询成功 `ready`”门禁；后台持久化与事件交接另行达到 `converged`。
- [x] 3.4 实现绑定稳定 `volume_id` 的持久化按卷恢复队列、`waitingToRetry`/`recovering` 分类和确定性公平调度；存在首次任务时恢复任务最多占用 `max(1, floor(W / 2))` worker，并以服务状态变化、同一稳定身份卷重新上线、退避到期以及用户或操作系统结束应用后的下一次自然启动触发跨轮持续恢复；搜索功能不得主动关闭、重启或要求用户重启应用。
- [ ] 3.5 实现仅限介质/设备损坏、原卷不存在/离线、访问被拒绝的 `blocked` 非活跃终态与逐卷安全诊断，使用卷到达事件与不扫描 MFT/目录的低频轻量探测唤醒。
- [ ] 3.6 实现全局 `attentionRequired` 终态与 scope 变更门禁重算，确保仅剩外部不可满足卷时停止索引动画，其余情况保持恢复中且不伪报完成。
