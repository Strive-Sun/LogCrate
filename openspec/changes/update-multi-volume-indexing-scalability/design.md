## Context

Windows 搜索把本地固定 NTFS 卷作为独立任务并行枚举。当前应用最多运行 4 个卷 worker，索引服务也最多创建 4 个 pipe 实例，但服务接受第 4 个连接后仍会立即创建下一实例；达到传输层实例上限时该错误会终止服务循环。单卷流程还会先查询 USN、再建立新连接枚举 MFT，因此卷任务数、活跃连接数和服务监听实例数不是一一对应关系。

GUI 已按批次收到 MFT 记录，但当前仍把每卷完整记录保存在 `Vec<MftRecord>`，并把所有已完成卷保留在 `finalize_jobs` 中，等全部卷可搜索后才逐卷写入 SQLite/USN 快照。这个模型的峰值保留量由所有卷记录总和决定。

设计必须同时适用于当前 A:\–Z:\ 固定卷发现和未来由配置、VHD 或挂载点提供的更多范围；不能把提高常量当成扩展方案。

## Goals / Non-Goals

- Goals:
  - 对已发现范围数量 N 不设实现层面的特殊阈值，资源消耗由固定并发 W 和有界批次预算控制。
  - 服务在 W 个长请求活跃、额外客户端到达或客户端断开时仍保持运行和监听。
  - MFT 传输、暂存、路径解析、查询索引合并和持久化形成有界流水线，已完成卷及时释放内存。
  - 一个卷失败或离线时其它卷继续完成，失败卷进入公平、持久化的自动恢复队列；所有 scope 的查询快照成功前全局不得进入 `ready`，持久化与事件交接完成前不得进入 `converged`。
  - 服务异常停止后进行分轮有界、跨轮持续且可诊断的恢复，不形成紧密无限循环或 UAC 弹窗循环。
  - 仅明确介质/设备损坏、原卷不存在或离线、访问被拒绝进入稳定的逐卷阻塞状态，不让 UI 永久显示活跃索引；其它故障必须自动修复或降级后最终恢复成功。
- Non-Goals:
  - 不提高索引服务权限，不读取文件内容，不访问网络。
  - 不默认增加卷 worker 数量来追求吞吐；首版统一资源预算固定为 `W = 4`。
  - 不改变文件名切词、查询排序、监控目录或日志查看行为。
  - 不承诺同时运行与卷数量相同的 MFT 枚举。

## Decisions

### 1. N 个范围使用轻量注册表、有界 runnable window 和固定 worker 池

- 协调器用轻量 scope 注册表保存全部待处理范围的身份、generation 和阶段状态，这是随 N 线性增长且不可避免的最小元数据；未开始范围不保存 MFT 数据、pipe、暂存句柄或专用线程。
- 运行时从注册表分页填充最大 `Q = 2W` 的 runnable window，并在任务离开 window 后持续补充；首版只启动 `min(可运行任务数, W)` 个 worker，且 `W = 4` 是同时约束活跃卷、业务请求和打开暂存的内部资源上限。
- worker 在一个范围完成一次成功处理或失败尝试并释放其批次、pipe、暂存句柄后才能领取下一范围；失败范围按退避时间重新排队，不能永久占据 worker。
- 调度器分开首次/正常队列与已到期恢复队列；存在未尝试范围时，同时执行的恢复任务最多为 `max(1, floor(W / 2))`，并用确定性加权轮转分配剩余机会；正常队列清空后恢复队列可使用全部 W。
- 取消以 generation 为边界：重建、清除和暂停先阻止领取新任务，再等待活跃任务退出。

Alternatives considered:

- 每卷一个线程或 pipe：实现简单，但线程、句柄和内存随 N 增长，拒绝。
- 把上限从 4 提高到 10/26：只移动故障点并放大 IO 与内存竞争，拒绝。

### 2. pipe 接纳容量与业务执行容量分离

- 服务使用独立 accept loop，并始终保留创建或等待下一连接的能力；传输层实例上限不得等于已占满时无法再监听的业务 worker 上限。
- 连接成功后由应用层信号量授予最多 W 个业务槽位。无槽位时服务复用现有 v2 envelope 的 `Response::Error { code: 429 }` 作为 `busy/retryable` 响应并立即释放连接，不退出服务；只有 wire shape 确实不兼容时才提升协议版本。
- `CreateNamedPipeW`、`ConnectNamedPipe` 或客户端断开错误按可重试、停止请求和致命服务错误分类；正常容量饱和不得传播为服务主循环错误。
- 服务停止时先停止接纳新任务，再唤醒监听器并等待已接受请求有界退出，最后准确上报 stopped 状态。

Alternatives considered:

- 仅把 pipe 实例数改为 W+1：能修复当前临界值，但其它进程、探针和请求阶段仍可能消耗额外实例，且没有稳定背压协议，作为单独方案不足。
- 依赖客户端长轮询 pipe：无法保证服务仍存活，也不能区分忙与崩溃，拒绝。

### 3. 客户端使用状态感知的分轮恢复

- 客户端区分 pipe 忙、pipe 不存在、访问拒绝、服务启动中、服务已停止和协议不兼容。
- `busy/retryable` 使用带上限的退避并保持卷为排队/连接状态；不将其标记为完成或不可恢复失败。
- pipe 不存在时重新查询 SCM。每轮恢复中，服务已停止可自动启动一次并重新握手；本轮失败后记录原因、增加有上限的指数退避并把卷放回恢复队列，而不是结束整个 operation。
- 恢复队列、失败阶段、尝试次数、下次尝试时间和 operation scope 必须持久化；应用重启、服务状态变化、卷重新上线或退避到期时继续恢复。
- 自动恢复不得自动弹出 UAC。协议不兼容、安装损坏或服务启动失败属于软件故障，先尝试当前权限下的修复/替换，无法完成时必须自动降级到可读取该卷的兼容 provider 并最终索引成功；只有实际访问被拒绝时才可进入 `blocked`。

错误分类分为两组：

- 外部不可满足：操作系统明确报告原卷不存在/已离线、不可恢复介质或设备 IO 损坏、访问被拒绝且当前权限无法继续。它们进入 `blocked`，停止定时主动索引重试，以卷到达/移除通知为主要唤醒，并辅以有上限低频轻量健康探测。探测只重新核对稳定卷身份和可访问性，不打开 MFT 流、不执行目录遍历、不显示索引动画。
- 可恢复：pipe 忙或消失、服务启动中/意外停止、协议不兼容、安装损坏、自动启动失败、暂时共享冲突、暂时 IO、暂存或 generation 恢复、应用退出等。它们进入 `waitingToRetry` 或 `recovering`，或降级到兼容 provider；不得降级为完成或永久阻塞，并在卷可读且权限满足时最终成功。

单次错误文本或重试次数耗尽不能单独证明物理永久损坏。只有稳定的操作系统类别、卷枚举事实或明确权限拒绝才能进入外部不可满足组；未能证明的错误继续按可恢复处理并保留退避。

### 4. 恢复义务绑定稳定卷身份

- 每个卷范围同时保存稳定 `volume_id` 与可变的显示/挂载路径。Windows 首选规范化 Volume GUID path，并使用卷序列号与文件系统类型作为重用校验；盘符不得单独作为恢复身份。
- 卷重新到达时，只有稳定身份与原 scope 匹配才能继续旧 generation；同一盘符上出现的不同卷必须作为新 scope/新 generation 发现和索引，不得沿用原卷的暂存、USN 位点或完成状态。
- 原卷被不同卷占用盘符时，原 scope 保持“原磁盘已断开”的 `blocked`，新卷按当前发现范围加入新 generation；两者的查询结果和恢复义务不得混合。

### 5. MFT 使用独立按卷 SQLite 暂存和有界批次流水线

- 每个活跃卷把 MFT 批次写入独立、版本化的 SQLite 暂存文件，内存中只保留有界批次、路径解析工作集和提交缓冲。独立文件避免多卷暂存争用共享写锁，并复用现有 SQLite 依赖和事务恢复能力。
- 路径解析需要父引用图时，从按卷暂存中分批读取或使用受控的磁盘索引，不重新把完整卷图复制到多个内存集合。
- 查询索引合并继续由单一协调边界完成。一个卷查询结果核对成功后即可进入可搜索终态，并立即完成或排队执行该卷持久化；不得等待所有其它卷枚举完成才释放记录。
- 每卷暂存通过完成标记和 generation 标识提交。取消、崩溃或失败遗留的未完成暂存在下次启动隔离或清理，不覆盖 active 数据。

Alternatives considered:

- 保留每卷完整 `Vec`，只限制 W：峰值仍由 W 个超大卷决定，而且当前完成队列会累计全部卷，拒绝。
- 所有卷写同一个无边界 channel：慢消费者会导致生产者和内存无限堆积，拒绝。

### 6. 按卷自动恢复与查询完成/持久化收敛门禁

- operation 开始时冻结 `scope_set` 和 generation；每个包含范围通过发现、路径解析、查询索引发布与查询计数核对后进入 `ready`，完成 SQLite/USN 持久化、快照完成标记和有界事件交接后进入 `converged`。
- 一次可恢复失败进入 `waitingToRetry`/`recovering` 并按退避重新排队；已证实的物理损坏、卷离线或权限拒绝进入 `blocked`。这些状态都不会取消其它范围，但都阻止全局 `ready`。
- 至少一个范围保有可查询快照时，全局搜索继续提供已验证结果并明确标记不完整、恢复中或阻塞范围；这是过程可用性，不是 operation 完成。
- 只有 `scope_set` 中所有范围均为 `ready`，查询总数与各范围完成快照核对一致，才发布全局 `ready` 和完成时间。
- 全局 `ready` 发布后持久化可在后台继续，不得重新显示“正在索引”；任一卷未 `converged` 时必须显示独立的后台保存/恢复诊断，并持续自动恢复，只有所有非 `blocked` 卷收敛后才发布全局 `converged`。
- 当所有非 `blocked` 范围均为 `ready` 且 `converged`，没有 `pending`、活跃扫描、后台持久化或到期恢复任务，且至少一个范围为 `blocked` 时，全局进入稳定的 `attentionRequired`，停止“正在索引”动画并逐卷显示阻塞原因；该状态不是 `ready`，也不表示后台仍持续扫描。
- 用户明确排除一个卷属于 scope 变更：取消旧 generation，生成新的 `scope_set` 后重新计算完成门禁；系统不得通过隐式忽略失败卷来满足门禁。
- 慢卷和恢复卷不阻塞已完成卷发布，也不阻止队列中的其它卷在 worker 可用后开始；恢复调度必须公平，避免一个持续失败卷饿死其它卷。

## Risks / Trade-offs

- 磁盘暂存增加本地 IO 和实现复杂度 → 使用按卷版本、批量事务和现有应用数据目录，并通过基线比较吞吐与写放大。
- 单卷立即发布会增加 Tantivy 提交次数 → 由协调器合并有界批次，并记录每卷提交耗时和段数量。
- 自动重启可能掩盖持续崩溃 → 每轮只允许有限自动启动/重连次数，跨轮使用有上限退避并保存首次失败、最近失败和尝试计数。
- 永久离线或实际访问被拒绝的卷无法由普通权限进程保证物理恢复 → 保持 operation 为 `blocked` 且绝不发布全局 `ready`，等待卷恢复、权限修复或用户显式变更 scope。单纯索引服务需要修复不能代替“卷访问被拒绝”证据。
- 过程中的部分结果、查询完整和耐久收敛容易混淆 → 保持每卷状态为事实来源，UI 分开显示“部分结果可查询”、“所有卷 `ready`”和“后台已 `converged`”。
- 盘符复用可能把不同物理卷接上旧恢复记录 → 恢复键使用稳定卷身份，并为“原 D: 拔除后新卷占用 D:”增加回归。
- 将暂时错误误判为物理损坏会破坏成功保证 → `blocked` 只接受明确的卷枚举、介质/设备 IO 或权限证据；未知错误保持可恢复并接受退避。
- 真实十盘设备难以在 CI 提供 → 使用可注入 provider/pipe 夹具覆盖大 N，Windows 真机至少验证容量边界、服务恢复和可用的多卷组合。

## Migration Plan

1. 先修正服务接纳和客户端状态分类，使用现有 v2 `Response::Error { code: 429 }` 表示可重试忙；只有不兼容 wire shape 变化才提升协议版本。
2. 引入独立按卷 SQLite 暂存格式时使用新版本目录，不原地破坏现有 active SQLite/Tantivy；首次运行可后台重建受影响卷。
3. 将协调器切换为完成即消费和按卷发布，保留旧 active 快照直到新范围核对成功。
4. 失败时删除或隔离该卷新 generation 的暂存，回退到旧 active 搜索结果并把该卷写入恢复队列；不删除用户文件，不结束其它卷。

## Resolved Decisions

- 首版 `W = 4`，作为可观测、可测试的内部资源上限；未来只能在新基线和新提案下改变默认策略。
- 首版使用独立按卷 SQLite 暂存文件；实施可调整 schema、索引和批大小，但不得改变 generation 隔离、崩溃恢复、清理和有界资源语义。
